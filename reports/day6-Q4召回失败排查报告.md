## 三、排查链条（关键：不要一上来就乱调参数）

```
假设1：TopK 太小，没召回死机分段
  → 改 TopK 3→5，门禁实测：指标完全持平，Q4 仍失败
  → 推翻假设，TopK 不是根因

分层定位：检索问题要分四层
  ① 数据层：分段在不在？
     → 知识库分段列表搜"重启"，Chunk-21 存在、内容完整（22字符）、已启用
  ② 全文检索能否命中？
     → 召回测试切全文检索，查"死机"返回 0 结果（Weaviate 中文分词/索引未建）
  ③ embedding 模型本身正常吗？
     → 用 DashScope text-embedding-v3 直接算余弦相似度：
       "死机" ↔ Chunk-21 死机重启 = 0.6696（应排第一）
       "死机" ↔ 其他分段 = 0.42~0.54（明显更低）
       → 模型正常，目标分段语义最相关
  ④ 结论：
     → Chunk-21 在 Weaviate 里的向量缺失/异常（很可能是 Day 2 上传时
        429 限流导致该分段 embedding 失败），分段在但向量没写入，不参与检索
```

**根因：Chunk-21 向量索引缺失（不是 TopK、不是模型、不是分块内容）**

---

## 四、修复方法

1. 编辑保存无效（Dify 检测内容未变，跳过重新 embedding）
2. **删除 Chunk-21 → 手动新建一条内容相同的分段**（强制重新生成向量）
3. 等待 5-10 秒，召回测试查"死机" → Chunk-21 排第一
4. 知识检索节点 TopK 改回 3（撤销无效改动，保持单一变量）
5. 重跑门禁 → 三项指标全部 1.0，Q4 修复

## 五、方法论提炼（面试可讲）

1. **一次失败不要只跑一次**：RAG 有非确定性，Q4 靠 Day4/5/6 多次评测才暴露规律
2. **质量门禁要快、稳、可复现**：用确定性规则指标（召回/答案/拒答），不依赖 LLM 评委；
   DeepEval 那类慢、花钱、有波动的评测放到发布前
3. **检索问题分层定位**：数据层 → 索引层 → 检索层 → 生成层；
   盲目调 TopK 解决不了"向量没入库"
4. **对照实验遵守单一变量**：先证伪 TopK（改 3→5 无效），再只改"向量修复"，
   用前后 JSON 数据对比，而不是凭感觉
5. **embedding 失败会"静默"**：分段显示"已启用"不代表向量正常，可用"召回测试 +
   直接算 embedding 相似度"交叉验证
6. **阈值是业务取舍**：基线 0.8 恰好放行 Q4，阈值卡多严取决于业务对漏答的容忍度
